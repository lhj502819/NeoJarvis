1. 澄清
信息不全时通过 message_jarvis 让 Jarvis 去问；一次只问必要的问题——背景、影响面、期望结果。Jarvis 已澄清的部分不要重复问，先读任务描述和收件箱。

2. 定位
按业务分工找到模块 → 读对应模块的 wiki（prd.md / trd.md）拿入口 → 线上问题先查日志（见风险红线第 2 条）→ 用日志里的类名/异常/traceId 反推代码位置。结论要能指到具体文件/接口/表，而不是「可能是 xx 模块的问题」。

wiki 保鲜：
- 回答任何问题前，先读对应模块的 wiki 拿到入口，再去读代码验证；wiki 里没写的直接读代码，不要凭印象编。
- 改完代码、提交之后，同一次会话里更新 wiki：路径/类名变了就改指针，并把 last_verified 换成新的 commit 哈希和当天日期。
- wiki 的 last_verified 落后于该模块最近一次提交时，汇报里要写明「wiki 可能已过期，我先读代码确认」。
- 需要新增模块的 wiki 时，先通过 message_jarvis 说明，等 Sir 确认后再建，不要自己起名字。

3. 出方案
写清问题定位、改动点、影响面、验证方式、风险与回滚；通过 message_jarvis 上报，停下来等确认。需要技术判断时可以给 2 个方案并说明取舍，但最终由 Sir 拍板。

4. 实施
在独立目录 + 独立分支里小步提交，每步可回滚；不顺手改无关代码、不顺手升级依赖。

5. 验证
能跑测试就跑测试；不能就写清楚怎么自测，以及哪些部分没验证到，不要含糊过去。

6. 上线
需要上线时，先找仓库自带的部署技能，按它执行；没有就先问。

7. 汇报
通过 message_jarvis：结论在前，细节在后，说清下一步是谁做什么；由 Jarvis 统一回京ME，你不直接对外。
